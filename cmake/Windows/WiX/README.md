WiX / MSI packaging prototype
=============================

An alternative to the NSIS installer (`cmake/package_nsis.cmake` +
`cmake/Windows/NSIS.template.in`), producing a Windows Installer `.msi` via
CPack's `WIX` generator.

**Status: prototype.** It is not wired into tag-triggered releases. To exercise
it, dispatch the `Release` workflow manually and set the
`windows_package_type` input to `wix`, or configure locally with
`-DPACKAGE_TYPE=wix`.

Layout
------

| File | Purpose |
| --- | --- |
| `cmake/package_wix.cmake` | CPack configuration; generates the fragments below |
| `openms_extras.wxs.in` | PATH entries, start menu shortcuts, file associations |
| `openms_patch.xml` | Wires those fragments into CPack's root feature |
| `tools/ci/validate-wix-authoring.sh` | Lints the authoring without Windows |

Requirements
------------

* CMake **>= 3.31** (`CPACK_WIX_VERSION`, needed to target WiX v4/v5).
  Note the project's own floor is still 3.24; only this packaging path needs
  the newer CMake.
* The .NET `wix` tool plus its UI extension:

  ```
  dotnet tool install --global wix --version 5.0.2
  wix extension add --global WixToolset.UI.wixext/5.0.2
  ```

  WiX v3 (`candle`/`light`) is EOL and needs .NET Framework 3.5; it is not
  used here.

What MSI gives us for free
--------------------------

These are ~6200 lines of vendored NSIS includes plus a large part of the 767
line NSIS template that have no counterpart here, because the Windows Installer
does the same job itself:

* **Uninstall bookkeeping** — `AdvUninstLog2.nsh` and the
  `UNINSTALL.LOG_OPEN_INSTALL` / `LOG_CLOSE_INSTALL` pairs wrapped around every
  install section. MSI tracks installed files in its own database.
* **Previous version removal** — `NSIS.template.in:620` onwards reads the
  registry, execs the old uninstaller, checks for leftovers and sets a reboot
  flag. CPack's default template emits `<MajorUpgrade>`.
* **PATH editing** — `EnvVarUpdate.nsh` (350 lines) and, with it, the hard
  requirement on a *patched* build of NSIS with 8k string support
  (`cmake/package_nsis.cmake:24-27`, pointing at the `OpenMS/NSIS` fork).
  MSI's `Environment` table appends, removes on uninstall and rolls back, with
  no string length limit.
* **Locked files and empty directories** — `REBOOT_ON_INCOMPLETE_DELETION`,
  `un.RemoveEmptyDirs`.

What had to be re-authored
--------------------------

`openms_extras.wxs.in`, ~90 lines: PATH for `bin/` and each third party tool
directory, four start menu shortcuts, and the eleven file type registrations
from `NSIS.template.in:69`.

Two things are worth knowing about how it is written:

* The third party PATH entries are resolved at **configure** time from
  `THIRDPARTY_COMPONENT_GROUP`, not by walking `share/OpenMS/THIRDPARTY` at
  install time the way `NSIS.template.in:471` does. MSI's `Environment` table
  is a build-time table. This is not a limitation in practice, because
  `install_thirdparty_folder()` already knows the list.
* File associations are written as explicit `<RegistryValue>` elements rather
  than `<ProgId>`/`<Extension>`/`<Verb>`. `Verb/@TargetFile` has to point at a
  `File` element, and the file ids are generated by CPack at packaging time
  (`CM_FP_<mangled path>`, see `CreateNewIdForPath` in `cmCPackWIXGenerator`),
  so a hand-authored fragment cannot reference them. Uninstall removes the
  registry values either way.

Known gaps against the NSIS installer
-------------------------------------

These are deliberate omissions in the prototype, not oversights:

1. **Per-user vs per-machine choice is gone.** The NSIS installer offers both
   via `NsisMultiUser` (3200 vendored lines). `CPACK_WIX_INSTALL_SCOPE` accepts
   `perMachine` or `perUser` but has no combined mode, so MSI would have to
   pick one; this prototype is `perMachine`. CMake's own documentation warns
   that installers built with different scopes cannot cleanly replace each
   other, so this is a one-way decision.
2. **No splash screen.** `advsplash` (`NSIS.template.in:605`) has no MSI
   equivalent; it would need a Burn bootstrapper, i.e. a second installer
   project wrapping the `.msi`.
3. **English only.** The NSIS installer offers German, English and French
   (`NSIS.template.in:203-205`). Multi-language MSI means either one `.msi` per
   culture or `.mst` transforms.
4. **No branding artwork.** WiX requires exactly 493x58 (banner) and 493x312
   (dialog). The existing NSIS bitmaps in `cmake/Windows/images` are 150x57 and
   164x314, so they cannot be reused and new artwork has to be drawn.
   `CPACK_WIX_UI_BANNER`/`_DIALOG` are therefore left unset.
5. **No upgrade from an existing NSIS installation.** `<MajorUpgrade>` only
   detects MSI products. A first MSI release would leave any NSIS-installed
   OpenMS in place, with both registered in Add/Remove Programs and both
   `bin` directories on `PATH`. Closing this needs a custom action that reads
   `SOFTWARE\OpenMS`'s `UninstallString` (the key `NSIS.template.in:620`
   writes) and runs the old uninstaller.
6. **Silent install flags change.** `/S /allusers /nothirdparty` become
   `msiexec /qn ADDLOCAL=...`. More standard, but it breaks existing scripts
   and the documented command lines in `NSIS.template.in:566`.

The component graph blocks the feature tree
-------------------------------------------

`OPENMS_WIX_COMPONENTS=ON` is expected to fail to produce anything sensible
today, and is off by default.

`cmake/package_nsis.cmake:86-88` forces `CPACK_MONOLITHIC_INSTALL`, so CPack's
component graph is currently dead code: the NSIS template globs files straight
out of the staging directory instead. Nothing has been keeping the component
names honest, and they are not:

* `applications` is declared in `cmake/package_components.cmake` with install
  types `recommended full minimal`, but every `install()` rule spells it
  `Applications`. CPack component names are case sensitive, so that
  declaration currently attaches to nothing — and it is the one covering the
  TOPP tools, TOPPView and TOPPAS.
* Nine further components are reachable on Windows but never declared:
  `Applications`, `Dependencies`, `OpenMSTestFramework`, `QtPlatformPlugin`,
  `cmake`, `headers`, `libraries`, `python_modules`, `thirdparty_headers`.
  (`libraries`, from the vendored sqlite3, looks like it was meant to be the
  declared `library`.) Two more, `TOPPShell` and `zzz`, exist only in the
  macOS packaging scripts and do not affect Windows.

In monolithic mode none of this matters. In feature-tree mode each of those
becomes a user-visible MSI feature with an auto-generated name and no install
type. Straightening the component graph out is a prerequisite for a component
based MSI, and is worth doing on its own merits.

Validating without Windows
--------------------------

WiX prints `The WiX Toolset only supports Windows` on startup and the final
bind step P/Invokes `msi.dll`, so no `.msi` can be produced off Windows.
Everything before that — XML parsing, schema validation, reference resolution,
linking — is managed code and runs anywhere. `wix build -o <file>.wixipl` stops
exactly at that boundary.

`tools/ci/validate-wix-authoring.sh` uses that to check the authoring on a
Linux runner (see `.github/workflows/wix-authoring-validate.yml`). It catches
malformed XML, misspelled elements and attributes, and component groups
referenced by `openms_patch.xml` that do not exist — that last one matters,
because an unreferenced fragment is silently left out of the `.msi` rather than
erroring.

Two traps it exists to catch, both of which bit while writing this prototype:

* **An empty fragment links cleanly.** An empty `<ComponentGroup>` is valid
  WiX, so a mistyped CMake variable feeding one of the `foreach()` loops
  produces an installer with, say, no file associations at all, and nothing
  complains. The script asserts expected element counts for this reason.
* **`configure_file()` substitutes an undefined `@VAR@` with the empty
  string**, so a typo in `openms_extras.wxs.in` does not leave a visible
  `@PLACEHOLDER@` — it leaves `Name=""`. The script greps for empty attribute
  values.

One local workaround: on Linux, *every* value of `Directory/@Name` trips
`WIX0389: ... is not a relative path`, because the check runs through Windows
path semantics. The script strips that attribute before linting; it carries no
information the reference checking needs. Verified against wix 5.0.2.

Also note XML comments cannot contain `--`, so the standard OpenMS copyright
header has to be written with a single dash in `.wxs` files.

Still unverified
----------------

Everything above the authoring level needs a Windows runner: ICE validation,
the installer UI, install/uninstall/upgrade/rollback behaviour on a real
machine, whether `light`/`wix build` copes with the Doxygen HTML tree (CPack's
WIX generator emits one `<Component>` per file, and `doc/CMakeLists.txt:327`
installs the whole tree), and the MAX_PATH headroom that
`.github/workflows/release.yml` currently works around with `C:/cpk`.
